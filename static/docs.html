Hevy Fatigue — Methodology & Reference

A technical walkthrough of the fatigue monitoring model: how training load is quantified, how metrics are computed, and the research behind each design decision.

01

Design philosophy

Hevy Fatigue is a subjective-first fatigue monitoring dashboard. Daily check-in scores are the primary signal — training load data from Hevy acts as a contextual modifier, not the core driver. The system is designed to surface clear information so that a fatigue-aware athlete can make their own decisions. It does not prescribe training adjustments.

This philosophy was chosen because objective training load metrics (volume, tonnage, sRPE) are well understood to be incomplete proxies for actual systemic stress. Factors like sleep quality, nutrition, life stress, and individual adaptation rate are captured better through subjective self-assessment than through bar-on-back math alone.

Core principle

A fatigue number without subjective context is noise. Subjective scores without load context lack resolution. The system combines both.

02

Check-in model

Each day, the athlete logs recovery signals on a 0-4 scale (0 = fresh / no issue, 4 = most fatigued / most limited). The backend normalizes these values to build a subjective fatigue component.

Field What it captures Role in model
tiredness Overall tiredness and lethargy Primary subjective fatigue input
perceived_recovery How recovered the athlete feels Primary subjective fatigue input
sore_quad_dom Knee-dominant soreness signal Contributes to soreness composite in fatigue formula
sore_posterior Hip/posterior-chain soreness signal Contributes to soreness composite in fatigue formula
sore_upper_push Upper-body push soreness signal Contributes to soreness composite in fatigue formula
sore_upper_pull Upper-body pull soreness signal Contributes to soreness composite in fatigue formula
joint_upper / joint_lower Upper and lower joint discomfort signals Advisory only - excluded from fatigue formula
Design note — joint health

Joint health is excluded from the fatigue formula intentionally. Joint discomfort is a different biological signal from systemic fatigue — it reflects tissue loading tolerance and injury risk, not necessarily overall recovery status. Including it in a weighted average risks suppressing the fatigue number when joint pain is the dominant concern, or inflating it when a minor ache is present alongside genuine freshness. It is surfaced as a standalone advisory on the dashboard instead.

Daily fatigue score

The subjective component is computed from normalized 0-4 check-in values, then scaled to a 0-20 fatigue score where 20 = most fatigued:

// Normalize each check-in field from 0-4 to 0.0-1.0
t = tiredness / 4
r = perceived_recovery / 4
s = (sore_quad_dom + sore_posterior + sore_upper_push + sore_upper_pull) / 16

// Subjective-first weighting from main.py
subjective_fatigue = (0.45 * t) + (0.30 * r) + (0.25 * s)

// Scale to 0-20
daily_fatigue_score = subjective_fatigue * 20

On days without a workout, the daily fatigue score is computed from check-in alone. On training days, training load is incorporated as a modifier (see §4).

02b

No check-in — pending state

When no check-in exists for the current day, the dashboard switches into a neutral pending state. The subjective score shows as —, the combined score shows as value* with a muted/unconfirmed treatment, and the recommendation copy changes from a fatigue-based recommendation to a check-in prompt.

  • Pattern stress cards render with muted styling and empty dots.
  • The stress label shows — instead of a numeric score.
  • Training load signals still compute normally from workout history; only the subjective component is absent.
  • The footer note remains: No check-in today — pattern signals based on training load only.
Design rationale

A neutral fallback of 10.0 is used for math only when the subjective score is null. It is never displayed as a real score, and it exists solely to keep the combined readiness math stable until the athlete completes today's check-in.

03

RPE & session RPE (sRPE)

Two rating systems are used depending on session type:

RPE — Rate of Perceived Exertion (Borg-derived, 0–10)

Used for individual strength and hypertrophy sets. In the powerlifting / RTS context popularized by Mike Tuchscherer, RPE describes proximity to failure on a given set:

RPEMeaning
10Maximum effort — no reps left in reserve (0 RIR)
9Could have done 1 more rep (1 RIR)
8Could have done 2 more reps (2 RIR)
7Could have done 3 more reps (3 RIR)
6Could have done 4+ reps; moderate effort
<6Light / warm-up effort
Reference

RPE for resistance training was formalized by Tuchscherer [1] as an adaptation of Borg's original perceived exertion scale [2]. The reps-in-reserve framing (RIR) is now widely used in sport science [3].

sRPE — Session RPE

Used for conditioning and cardio sessions. sRPE is a single whole-session perceived effort rating (1–10) collected after the session ends, multiplied by duration to yield a session load score. This method was developed by Foster et al. [4] and has extensive validation across endurance and team sports.

session_load = sRPE × duration_minutes

In Hevy Fatigue, sRPE is encoded in session titles using the @N delimiter convention (e.g. CON @7 = conditioning session at sRPE 7).

04

Stress calculation pathways

Four distinct pathways calculate training stress depending on session modality. Each produces a session stress score (SSS) in arbitrary units (AU) that feeds into the EWMA model.

Pathway A — Strength & hypertrophy

Stress is computed per set using RPE and tonnage (load × reps). Sets below RPE 6 contribute negligible stress and are filtered or heavily discounted.

// Per-set stress
set_stress = tonnage × RPE_factor

// tonnage = weight_lbs × reps
// RPE_factor = exponential curve peaking at RPE 10

// Session stress = sum of all set stresses
session_stress = Σ set_stress

The RPE factor applies a non-linear curve so that the difference between RPE 8 and RPE 10 is much larger than between RPE 6 and RPE 8 — reflecting the disproportionate neural and systemic cost of near-maximal effort.

Pathway A2 — HYP sRPE fallback

When a verified HYP session has duration and sRPE logged but at least half of its sets are missing RPE values, the session falls back to a session-level sRPE proxy. This covers circuit-style hypertrophy work and pump sessions where per-set RPE is often incomplete.

// Trigger: ≥50% of sets in the HYP session lack RPE values
fallback_load = (sRPE × duration_minutes) / HYP_SRPE_SCALE

// HYP_SRPE_SCALE = 29.0 in app settings defaults
session_stress = fallback_load
Why this exists

Hypertrophy sessions often blend circuits, short rests, and pump work that do not map cleanly to per-set RPE logging. Session-level sRPE gives the model a reasonable proxy so those workouts still contribute to stress without requiring perfect set-by-set input.

Pathway B — Conditioning

Uses Foster's sRPE method, then normalizes to a target AU range to keep conditioning sessions commensurable with strength sessions on the same scale:

raw_load = sRPE × duration_minutes

// Normalize with conditioning_scale (default 29.0)
session_stress = raw_load / conditioning_scale
Calibration note

The conditioning scaling factor is currently set conservatively and will be refined against real session data. The goal is that a hard 45-minute conditioning session at sRPE 8 produces a session stress score roughly comparable to a demanding strength session — not identical, but within the same order of magnitude so neither modality dominates CTL unfairly.

Pathway C — Cardio

Uses the same sRPE × duration normalization as conditioning, but applies a flat 30% central / 70% peripheral stress split and contributes zero stress to any pattern bucket. Cardio affects global ATL/CTL only.

// Cardio reuses the same conditioning_scale normalization
session_stress = (sRPE × duration_minutes) / conditioning_scale
05

Session modality classification

Session type determines which stress pathway and which movement pattern distribution applies. Detection is two-layer:

Layer 1 — Title keyword matching: Hevy session titles follow a convention using codes that are parsed first. Mixed sessions use the + operator.

CodeModalityStress pathway
STStrength (max effort)Pathway A
HYPHypertrophyPathway A
CONConditioning (CrossFit-style, Strongman)Pathway B
CARCardio (running, cycling, rowing, etc.)Pathway C
ST+CONMixed strength + conditioningPathway A + B

Layer 2 — Exercise-level analysis: If no recognized code is found in the title, the system analyzes the exercises in the session to infer the most likely modality. This handles legacy sessions and sessions logged without title conventions.

sRPE encoding

For conditioning sessions, the sRPE value is encoded in the title after the @ delimiter: CON @7 means a conditioning session at sRPE 7. If no @N is present, a default sRPE is applied and flagged.

05b

Workout title tagging convention

Hevy Fatigue reads session titles from the Hevy app to determine modality and sRPE. For the system to classify your sessions correctly, titles should follow this convention. Sessions without recognized codes are still processed — the classifier falls back to exercise-level analysis — but title tagging is the most reliable path.

Modality codes

CodeUse forExample title
STMax effort strength (powerlifting-style, heavy singles/triples)ST — Back Squat
HYPHypertrophy (moderate load, higher rep, bodybuilding-style)HYP — Upper Push
CONConditioning — CrossFit-style WODs, Strongman, metabolic workCON @8 — Yoke + Farmers
CARCardio — running, cycling, rowing, machine-based aerobic workCAR @6 — Easy Run

sRPE encoding for conditioning and cardio

Conditioning and cardio sessions require a session RPE value to calculate load. Encode it in the title using the @N delimiter, where N is your whole-number sRPE (1–10):

// Format: [CODE] @[sRPE] — [description]
CON @8 — Devil Press AMRAP
CAR @5 — 30min Easy Row

If no @N is present on a conditioning or cardio session, the system applies a default sRPE and flags the session in the verification queue for manual review.

Mixed sessions

Use the + operator to indicate a session that spans two modalities — for example, a strength block followed by a conditioning finisher:

ST+CON @7 — Deadlift + Prowler

Mixed sessions are detected and flagged in the verification queue with a note explaining the split. Each component's stress is calculated through its respective pathway.

Strongman sessions

Strongman training (yoke, farmers, log press, atlas stones, etc.) is classified under CON. The conditioning stress pathway handles the mixed aerobic/strength demand of event training better than the per-set RPE model used for ST/HYP.

No code present?

If a session title has no recognized code, the classifier analyzes the exercises in the session to infer modality. The inferred result and a confidence score are shown in the verification queue — you confirm or correct it before it affects your metrics. See §05c Workout importer for details on the verification queue.

05c

Workout importer

Hevy Fatigue connects to the Hevy API to pull your workout history into the local database. The importer is designed to be lightweight and respect API rate limits — it does not run automatically in the background on a continuous schedule.

How sync works

Sync is triggered manually via the Sync button on the Workouts tab. Each sync pulls the most recent 7 sessions from Hevy using the workouts/events endpoint, which returns only changes since the last sync rather than re-fetching your entire history. On first-ever sync, a full historical fetch is performed to populate the database.

A cooldown period is enforced between syncs to prevent API rate limit issues. If you trigger a sync and see a cooldown message, wait the indicated time before retrying.

Verification queue

Every imported session lands in the verification queue on the Workouts tab — including sessions with clear title codes. This is intentional. Auto-classification is never trusted blindly: a misclassified session with an incorrect modality or missing sRPE will corrupt your stress calculations silently. Manual verification takes seconds and ensures the data feeding your metrics is correct.

For each queued session you will see:

  • The detected modality and confidence score
  • A note if a mixed session was detected or sRPE was missing
  • A dropdown to correct the modality if the classifier got it wrong
  • A duration field and conditional sRPE field for conditioning/cardio sessions

Verified sessions are written to the stress model and begin contributing to your ATL, CTL, and TSB. Unverified sessions in the queue do not affect your metrics.

Reclassification without re-syncing

If you update the title tagging convention on old sessions in Hevy, or want to re-run the classifier after a settings change, use the Reclassify Sessions button in Settings → Session Processing. This re-runs the classifier against all locally stored sessions without hitting the Hevy API and without consuming your sync cooldown. Manually verified sessions are not overwritten unless you explicitly request a full reclassify.

Force Full Sync (recovery)

Normally, Sync Now is incremental: it pulls only changes since the last sync, which is fast and API-friendly. In rare cases — after a data integrity issue, a botched canonical rename, or if you suspect orphaned or stale sessions — you can perform a Force Full Sync to delete and reimport your entire workout history from Hevy.

Important: Force Full Sync deletes all imported sessions and sets, then re-downloads everything. Your daily check-in history and canonical exercise names are always preserved. When you click Force Full Sync, a confirmation dialog appears. Confirm only if you understand the implications.

Force Full Sync is found in Settings → Hevy Sync, styled as a secondary button to discourage accidental use. Once initiated, both the Sync Now and Force Full Sync buttons become inactive until the reimport completes. If a full sync fails partway through (e.g., API timeout), an error message will tell you to retry or restore from backup — the system never silently leaves you with an empty workout table.

Diagnostics page

The Diagnostics page (/static/diagnostic.html) provides a lower-level view of what the importer has pulled: session volume, 7-day and 28-day workout summaries, and raw session data. If something looks wrong in your metrics and you're not sure why, diagnostics is the first place to look — it shows you exactly what data the system is working with. See §10 Diagnostics page for the full workflow.

06

Movement pattern buckets

To track fatigue at a finer granularity than "total load," session stress is distributed across four movement pattern buckets. This allows the system to detect, for example, that posterior chain fatigue is accumulating even when overall training volume appears moderate.

Knee dominant
30%
Squat, lunge, leg press patterns
Hip dominant
30%
Deadlift, hinge, hip extension
Push
20%
Press, push-up, dip patterns
Pull
20%
Row, pull-up, curl patterns

Each exercise in exercise_mappings carries percentage weights across the four pattern columns (pct_quad_dom, pct_posterior, pct_upper_push, pct_upper_pull). Session stress is apportioned to each pattern bucket proportionally based on these weights. For conditioning sessions where no exercise mappings exist, the system falls back to an equal 25/25/25/25 distribution across all four buckets.

Each pattern bucket runs its own parallel EWMA, producing per-pattern ATL, CTL, and TSB. This powers pattern-level trend visualization on the dashboard.

Pattern stress dots

Pattern stress dots use _pattern_tsb_signal(tsb, ctl) to turn per-pattern TSB into a normalized stress signal. The implementation is: clamp(-tsb / ctl, 0.0, 1.0), rounded to 3 decimal places, and it returns 0.0 when CTL ≤ 0.

// Per-pattern stress signal
signal = clamp(-tsb / ctl, 0.0, 1.0)
// Return 0.0 when CTL ≤ 0; round to 3 decimals
DotsLabelMeaning
1FreshFresh / underloaded
2Min. StressLight strain, mostly green
3Normal StressExpected training load
4Moderate StressApproaching caution territory
5High StressHigh fatigue / red flag
Dot colors

One-dot freshness uses the accent color. Two- and three-dot states use the success/green family. Four-dot stress uses the warn/amber color. Five-dot stress uses the danger/red color.

How pattern labels are derived

Pattern labels are not stored as a separate string in exercise_mappings. The app derives them from the pct columns using the movement split stored in the mapping table:

ConditionLabel
is_conditioning = trueConditioning
Otherwise, argmax across pct_quad_dom, pct_posterior, pct_upper_push, pct_upper_pullKnee / Hip / Push / Pull
All pct values are zeroUnassigned
Tie-break order

If two or more pct columns are tied for the maximum value, the app uses insertion order to break the tie: Knee → Hip → Push → Pull.

06b

Canonical exercise names

The canonical naming tool lets you assign a preferred display name to any exercise, overriding whatever name Hevy uses. This is useful when Hevy's default exercise names don't match your naming convention, or when you've renamed a custom exercise in Hevy but want Hevy Fatigue to reflect the new name immediately.

How it works

Hevy Fatigue tracks exercises by their internal Hevy ID, not by title. When you set a canonical name for an exercise, Hevy Fatigue stores the alias and uses it everywhere — in Movement Trend, exercise mappings, and stress calculations — regardless of what name Hevy sends during sync.

When to use it

  • A default Hevy exercise has a name you want to standardize (e.g. "Incline Bench Press (Dumbbells)" → "Bench Press, Dumbbell, Incline")
  • You renamed a custom exercise in Hevy but Hevy Fatigue still shows the old name
  • You want all historical data for an exercise to reflect a new name without waiting for a future workout to sync

How to set a canonical name

  1. Go to Patterns
  2. Find the exercise and click Edit
  3. Enter your preferred name in the Canonical Name field
  4. Save — Hevy Fatigue immediately updates all historical workout data for that exercise to the canonical name

What happens on sync

Every time Hevy Fatigue syncs with Hevy, incoming exercise titles are checked against the canonical table by exercise ID. If a canonical name exists, it overwrites whatever title Hevy sent — so the canonical name always wins.

Clearing a canonical name

Leave the Canonical Name field blank and save. Hevy Fatigue removes the alias and reverts to using whatever title Hevy sends on the next sync. Your pattern mapping is preserved.

Limitations
  • Canonical names only work for exercises that have been synced at least once — Hevy Fatigue needs the Hevy exercise ID to create the alias.
  • Exercises with a null exercise ID from the Hevy API cannot be canonically named. These are rare but will be flagged in the exercise list.

07

EWMA — ATL, CTL, and the time constants

The core of the load model is an Exponentially Weighted Moving Average (EWMA). Two EWMAs with different decay rates are computed in parallel:

MetricFull nameTime constant (τ)What it captures
ATLAcute Training Load7 daysRecent fatigue / short-term stress
CTLChronic Training Load42 daysFitness / long-term training capacity

EWMA recurrence formula

// Decay factor from time constant τ (days)
λ = 2 / (τ + 1)

// EWMA update rule (run daily)
EWMA_today = load_today × λ + EWMA_yesterday × (1 - λ)

// For ATL: λ = 2/(7+1) = 0.25
// For CTL: λ = 2/(42+1) ≈ 0.0465

On rest days, load_today = 0, so both ATL and CTL decay toward zero over time. ATL decays quickly (7-day window), CTL decays slowly (42-day window).

Origin of these constants

The 7-day and 42-day time constants derive from Banister's Impulse-Response model [5], adapted into training software by Coggan and Allen [6] for cycling power data. They are widely used heuristics — not derived from first principles — and their validity has been debated in the literature [7]. This system uses them as a reasonable starting point, not as precise biological claims.

Stabilization period

Because CTL has a 42-day window, the model requires approximately 6–8 weeks of consistent check-in history before CTL values are meaningful. Early CTL readings are systematically underestimated (the EWMA hasn't "filled up" yet). Values should be interpreted with caution during this ramp-up period.

Important

CTL is still building during the initial deployment period. Numbers will stabilize meaningfully after 6–8 weeks of consistent data. Early TSB readings should be treated as directional, not precise.

08

TSB & training state

Training Stress Balance (TSB)

TSB is the difference between fitness (CTL) and fatigue (ATL). It represents the net "readiness" signal from the load model alone:

TSB = CTL - ATL
TSB rangeTraining state
≥ +8Underloaded
+3 to < +8Slightly Fresh
-5 to < +3Balanced
-10 to < -5Slightly Fatigued
< -10Fatigued

Training state labels

Training state labels are resolved from TSB thresholds in the API settings. They describe load balance relative to recent fitness, not a directive:

Underloaded
Fitness is significantly outpacing recent training stress.
Slightly Fresh
Fitness outpacing fatigue; recovery is ahead of training.
Balanced
Fitness and fatigue are well matched; normal training state.
Slightly Fatigued
Fatigue is outpacing fitness; accumulated stress is present.
Fatigued
Fatigue is significantly elevated relative to current fitness.
Display note

TSB-derived state and subjective fatigue score are intentionally displayed separately on the dashboard. They measure different things: TSB reflects objective load history; the fatigue score reflects how the athlete actually feels. A low TSB (high fatigue load) alongside a subjectively good check-in is useful information — not a contradiction to be resolved.

08b

Fatigue score display

The fatigue score is displayed in the format X / 20, where 20 is maximum fatigue. This reinforces the scale's meaning at a glance — a score of 14.4 reads as "14.4 out of 20" rather than an opaque raw number.

On training days, the raw check-in fatigue score is adjusted by a training load modifier before display:

// Load modifier: how hard was today's session relative to baseline?
load_modifier = clamp(relative_delta × 1.2, -1.5, 1.5)

// Bounds in main.py: −1.5 to +1.5 points
// Final displayed score (clamped 0–20)
adjusted_fatigue = clamp(check_in_score + load_modifier, 0, 20)

The modifier is intentionally small — it nudges the check-in-derived score upward after an unusually hard session, but never overrides it. The subjective score remains dominant.

09

Joint health advisory

Joint health is collected as two separate fields (joint_upper and joint_lower) on a 0-4 scale. It is processed separately from the fatigue formula.

On the dashboard, joint health appears as a standalone advisory indicator. It is interpreted as a tissue loading signal:

Joint score (0-4)Advisory levelDashboard behavior
0-2noneNo joint warning row is shown.
3advisoryJoint advisory row is shown for the affected region.
4warningHigher-severity advisory row is shown for the affected region.

The advisory is informational only. The system makes no assumptions about which joints are affected or which exercises should be modified — that judgment belongs to the athlete.

10b

AI assistant

The AI tab provides a chat interface for training-context questions. It is a backend-proxied OpenRouter client: the user's API key is stored encrypted server-side and is never exposed to the browser.

The model picker offers preset OpenRouter models plus a custom model input. The current selection persists across sessions via localStorage under ai_preferred_model.

Assistant responses are rendered with marked.js, so markdown formatting is preserved in the chat output.

System context

The system prompt is built from the current fatigue state, ATL / CTL / TSB, the latest check-in scores, and the last 3 sessions with per-exercise volume detail. The assistant is context-aware but not prescriptive — it informs, it does not instruct.

Requirement

The AI assistant requires an OpenRouter API key configured in Settings before it can send messages.

11

Known limitations

EWMA stabilization: Both ATL and CTL require historical data to stabilize. Expect 2–3 weeks before ATL is reliable and 6–8 weeks before CTL is meaningful. Early TSB values are directional only.

sRPE accuracy: Session RPE is a subjective self-report and is known to be influenced by mood, expectations, and recall timing. Foster et al. recommend collecting sRPE 30 minutes post-session to reduce bias [4].

Conditioning scaling: The factor k used to normalize conditioning load to strength load units is a calibration estimate. It should be revisited after several weeks of mixed-modality data.

Individual variation: All time constants (7-day ATL, 42-day CTL) are population-level heuristics. Individual adaptation rates vary — some athletes recover faster, some slower. These defaults are a starting point.

Exercise classification: Automatic movement pattern classification relies on exercise name matching. Novel exercises, variant naming, or exercises not in the classification dictionary may be misclassified or unclassified.

No injury prediction: This system does not predict injury risk. Joint health advisory scores are self-reported and are informational context, not diagnostic output.
